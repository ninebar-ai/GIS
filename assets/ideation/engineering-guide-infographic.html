Engineering Guide · companion

What the guide looks like when you actually use it.

The guide is a document. This is the same thing as a working session — a simulated editor showing what changes on screen when you scaffold a POC, join a platform mid-build, or hand your work to someone else.

7 tabs 3 step-through simulations Engineering Kit paths Companion to GSD Core Simulated — not live tooling

Agents write weeks of code in an afternoon. The reasoning stays in one person's head.

That gap is what the guide closes. Not by slowing anyone down — by making the unspoken parts of a project recoverable by the next person who opens the repo.

When one person builds fast with an agent, the conventions, the rejected approaches and the reasons behind each shortcut live in their chat history. When a second person opens that repository the next morning, every unspoken thing has quietly become a bug: a convention they can't see, a decision they can't recover, a shortcut they'll step on.

The guide answers three questions the same way in every repository — how do we start something new, how do we join something that already exists, and how do we hand work over. Those are tabs 03, 04 and 05. The Engineering Kit on tab 07 turns each of them into a ready-to-paste agent session.

Outcome A

Ship at agent speed

The guide is not a brake. It's what lets a small team keep a large codebase honest while still writing at velocity.

Outcome B

Any repo, any of us

Every project follows the same shape, so anyone can open any repository and understand how it thinks in under an hour.

Outcome C

No re-argued basics

Stack choices, review rules, secrets handling — decided once, enforced by tooling, never re-debated per project.

One rule above all

If a machine can check it, it belongs in CI or a git hook — not in the guide. The guide covers the judgment calls tooling can't make. Everything else is code.

Where the failure actually happens

Not at the moment of writing. At the moment of transfer — a second developer, a new week, a returning author. The three simulations in this companion are each built around one of those transfer points.

Moment A · tab 03

Scaffolding a new POC

Day 0, idea to running skeleton. The moment where a wrong stack choice compounds for months.

Moment B · tab 04

Joining a platform in flight

Someone has been building for weeks. You need a working mental model in a morning, not a fortnight.

Moment C · tab 05

Handing off internally

Rotation, leave, phase completion. The context in your head has to survive the calendar.

Four artefacts, four different lifespans.

Fuse them into one file and the whole thing rots the day a tool renames a command. So they're deliberately separate, held together by cross-references.

Fig 01  ·  Four layers, one daily loop
Layer 1

Engineering Guide

Principles, tiers, review discipline, agentic standards. The judgment calls. Read on joining; referenced at every review.

Layer 2

AGENTS.md & CLAUDE.md

Per-repo rules the agent actually reads. Under 150 lines. AGENTS.md is portable; CLAUDE.md stays thin.

Layer 3

GSD Core

The workflow engine. Drives discuss → plan → execute → verify → ship, and persists state into .planning/.

Layer 4

Enforcement

Pre-commit hooks, CI stages, branch protection. Deletes half the prose in the guide by turning rules into checks.

Why the split matters

A guide that also documents commands breaks the week a tool renames one. Keeping the layers separate means a tool release touches one file, not the standard everyone reads.

And around all four — the Engineering Kit

The four layers describe how the practice is structured. The kit is how you start: for each moment, the files to load into an agent session, the prompt to paste, and the artifact you should end up with. The guide owns the why; the kit owns the how, right now, in five minutes. See tab 07.

The variant case — inherited, non-compliant code

    
Client handover, an old internal project, a spike that quietly became load-bearing. The specific danger:
      an agent turned loose on an undocumented codebase invents conventions and writes confident
      code in a house style that was never there. The playbook: assess before touching, make commit #1 an
      AGENTS.md describing reality including the ugly parts, write characterisation tests before any
      change, no drive-by refactoring, and make an explicit adopt / wrap / rebuild decision with a tier attached.

  







  

    
GSD keeps the trail. It does not keep the reasons you threw things away.

    
A handoff is now two handoffs — human to human, and context to the next person's agent.
      Anything left only in your chat history is gone.

Vibe coding isn't banned. It's fenced.

    
Riffing with an agent, no plan, ship if it works, is a legitimate mode. The guide names it
      honestly and refuses to let it become production by accident. That fence is the tier system.

  


  

    

      
Tier 1
Spike

      
Answer one question. Days. Fake data only. No tests required. Push to main.
        Print debugging is fine.

      
    
        
  • Vibe coding encouraged
    • 
        
  • GSD skipped, or one-shot
    • 
        
  • Review: none
    • 
      

    

    

      
Tier 2
POC / Demo

      
Show it works. Weeks. Internal or one client. Sample or masked data.
        Happy-path tests plus an eval set. Self-merge PRs allowed.

      
    
        
  • Vibe coding constrained — plan per phase
    • 
        
  • GSD runs with --mvp
    • 
        
  • Review: one reviewer, skim
    • 
      

    

    

      
Tier 3
Platform

      
Run the business. Years. Real users, possibly PII. Coverage floor, auth on
        every endpoint, alerts, runbook. Protected main.

      
    
        
  • Vibe coding not allowed
    • 
        
  • GSD runs with --tdd
    • 
        
  • Review: line-by-line on risk areas
    • 
      

    

  


  

    
The promotion rule

    
A Spike is never promoted by editing it. A POC is never promoted by editing it. Promotion means: take what
      you learned, write it as a specification, and rebuild at the higher tier. Reuse the ideas, the schema, the
      prompts, the eval set — not the code.

  


  
The failure this prevents is the most common one in agent-assisted development: a demo built in
    two days quietly becomes the thing a client depends on, carrying every shortcut taken when nobody was watching.
    Naming the tier out loud, in the README and in AGENTS.md, is what makes that impossible to do by accident.


  

    
Not this
    
      
  1. Ship a POC to a real customer without rebuilding at Platform tier
    2. 
      
  2. Let the agent invent a house style on an inherited codebase
    3. 
      
  3. Merge a 2,000-line diff because "the tests pass"
    4. 
      
  4. Skip the eval set because "we'll add it later"
    5. 
      
  5. Concatenate a prompt inline in business logic
    6. 
      
  6. Trust tool output without treating it as untrusted input
    7. 
      
  7. Edit a plan while the phase is executing
    8. 
    

    
This instead
    
      
  1. Write the POC as a spec, then scaffold Platform tier from it
    2. 
      
  2. Commit #1 on inherited code is a truthful AGENTS.md
    3. 
      
  3. Cap PRs at ~400 lines; if a phase produces more, the phase was too big
    4. 
      
  4. Twenty real examples of a "good answer" is a precondition to starting
    5. 
      
  5. Prompts live in files, in git, versioned, reviewed like code
    6. 
      
  6. Every retrieved or returned string is untrusted until proven otherwise
    7. 
      
  7. Plans are immutable during execution — change between phases, not within
    8. 
    

  


  
The ten non-negotiables

  
These live verbatim in the AGENTS.md of every repository. They apply at every tier, Spike
    included, because their first failure is also their most expensive. They're what the reviewer scans for on
    every diff — and they're the shape of how agents fail, written down so the reviewer looks on purpose.

#RuleEnforced by

    
      
01Never invent a library. If unsure a package exists, stop and ask.Review

      
02Never widen scope beyond the plan. Extra ideas go in the PR description, not the diff.Review

      
03Never edit a test to make it pass. Fix the code, or flag the test as wrong.Review

      
04No secrets, keys or customer data in code, prompts, logs or traces.Hook + CI

      
05Every external call has a timeout and an explicit error path.Review

      
06Every new endpoint has input validation and a test.CI

      
07No silent exception swallowing.Lint

      
08Configuration comes from the environment. Never hardcode.Review

      
09Migrations are additive and reversible. Destructive changes need human sign-off.Review

      
10Past 400 lines in a file, or a third copy of a block — propose a refactor.Review

The point

    
We're not writing a guide for its own sake. We're writing the smallest set of shared conventions that lets
      a small team ship agent-assisted software the whole team can trust. Anything that doesn't earn its place
      should be deleted — including from here.

  







  

    
The guide is the reference. The kit is the on-ramp.

    
Sixty pages is what a reviewer applies at the gate — not what anyone reads to start a
      piece of work. The kit is the operational layer: for each moment, the exact files to load, the prompt to
      paste, and what you should end up holding.

  


  

    
Engineering Guide
Owns the why

      
Comprehensive, dense, read cover-to-cover once. Principles, tiers, review discipline, agentic standards.
        It is the source of truth, and it is what the kit is checked against.

    
Engineering Kit
Owns the how, right now, in five minutes

      
Rules, templates and prompts. Hand the folder to an agent or a new teammate and they can start real work
        without re-reading the guide first.

  


  
What's in the folder

  
Three kinds of thing, deliberately separated by how often they change — the same layering
    principle as the guide itself.

How the kit evolves

  

    
Rules
Quarterly

      
The guide's judgement calls, extracted. They change when the guide changes, not per project.

    
Templates
Per project

      
Copy into your repo, then edit the copy. Never edit in place — templates stay clean so the next person
        gets a clean start.

    
Prompts
As we learn

      
Small, sharp edits as we find out what agents actually need. They're starting points, not scripts —
        read what you're pasting.

    
The guide
Owns the why

      
If the guide and the kit disagree, the guide wins — and the drift is a bug in the kit,
        so flag it.

  


  

    
Two things people get wrong

    
Load the whole guide, not excerpts. It's short enough, and excerpting loses the
      cross-references that make it work. And the kit is context, not law — it exists to get you
      moving in five minutes, not to replace the judgement the guide is asking you to exercise.

  


  

    
The trimming rule

    
Every new rule or template must name the incident that caused it. A kit nobody trims is a kit nobody
      uses — which is the same rule the guide applies to itself.
